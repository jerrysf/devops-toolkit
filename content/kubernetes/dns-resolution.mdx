## Symptoms

- App logs show `ENOTFOUND`, `NXDOMAIN`, or `Temporary failure in name resolution`.
- Requests to a ClusterIP **work**, but the same request by hostname fails.
- Either one service name fails (record problem) or everything fails (CoreDNS problem).

The subtlety: DNS can be perfectly healthy while the *record* is missing. Different problem, different fix.

## Common causes

1. **Service has zero endpoints** — the selector matches no pods; the record effectively doesn't exist. Most common.
2. **CoreDNS pods down or crashlooping** — cluster-wide resolution failure.
3. **Wrong name** — `svc` only resolves same-namespace; cross-namespace needs `svc.ns` or FQDN.
4. **NetworkPolicy blocking port 53** — queries *time out* rather than NXDOMAIN.
5. **ndots/search-domain** — short names expand wrong; FQDN still resolves.
6. **Node DNS misconfiguration** — custom kubelet resolvConf, systemd-resolved issues (rare).

## Diagnosis

### Step 1 — Test from inside the cluster

<Safety level="readonly" /> `kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- nslookup kubernetes.default`

```
Server:    10.96.0.10
Name:      kubernetes.default
Address 1: 10.96.0.1 kubernetes.default.svc.cluster.local
```

The built-in name resolving proves CoreDNS answers queries — the problem is the specific record, not the server.

### Step 2 — Test the failing name, short and FQDN

<Safety level="readonly" /> `kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- nslookup backend.default.svc.cluster.local`

- FQDN resolves, short doesn't → search-domain/namespace issue.
- Both NXDOMAIN → record doesn't exist → step 3.
- Both **timeout** → query never reaches CoreDNS → step 4.

### Step 3 — Check the Service's endpoints

<Safety level="readonly" /> `kubectl get endpoints backend -n example-ns`

`<none>` endpoints = selector matches nothing. Compare the selector against real pod labels:

<Safety level="readonly" /> `kubectl get svc backend -n example-ns -o jsonpath='{.spec.selector}'`

<Safety level="readonly" /> `kubectl get pods -n example-ns --show-labels`

A Service's ClusterIP DNS record only exists while it has endpoints — a selector/label mismatch produces genuine NXDOMAIN.

### Step 4 — Check CoreDNS and NetworkPolicy

<Safety level="readonly" /> `kubectl get pods -n kube-system -l k8s-app=kube-dns`

<Safety level="readonly" /> `kubectl get networkpolicy -n example-ns`

A policy selecting the pod without an egress rule for port 53 silently kills resolution — and CoreDNS logging `NXDOMAIN` proves queries *arrive* (rules out NetworkPolicy).

## Root cause analysis

| Evidence | Root cause |
|---|---|
| FQDN NXDOMAIN + endpoints `<none>` | Selector/pod-label mismatch |
| Everything NXDOMAIN cluster-wide | CoreDNS down |
| FQDN works, short doesn't | ndots/search-domain or wrong namespace |
| Timeouts, not NXDOMAIN | NetworkPolicy or kube-dns endpoints empty |
| Direct ClusterIP works, name doesn't | Confirms DNS-layer, not connectivity |

## Resolution

- **Selector mismatch:** update `svc.spec.selector` to the pods' current labels (or relabel pods). Endpoints populate within seconds.
- **CoreDNS down:** <Safety level="modifying" /> `kubectl rollout restart deployment coredns -n kube-system` — brief cluster-wide DNS blip during restart.
- **Namespace:** use `svc.ns` or FQDN in app config; never rely on short names cross-namespace.
- **NetworkPolicy:** <Safety level="modifying" /> add egress allowing UDP/TCP 53 to kube-system.

## Verification

<Safety level="readonly" /> `kubectl get endpoints backend -n example-ns` — populated.

<Safety level="readonly" /> `kubectl exec app-pod -n example-ns -- nslookup backend` — resolves.

Then the real check: the application's own health call succeeds by name.

## Prevention

- Alert on Services with zero endpoints — almost always a bug.
- Rename pod labels and update Service selectors in the same change; drifting them is the #1 cause.
- Standardize on FQDN for cross-namespace calls.
- Try the [DNS simulator scenario](/simulator/dns-resolution) to practice.

## Kubernetes version notes

Applies to Kubernetes 1.28–1.34. Pods with `dnsPolicy: Default` resolve via node DNS, not cluster DNS — check the pod spec if one pod behaves oddly.
